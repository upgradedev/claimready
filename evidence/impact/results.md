# Impact runs, scored

Generated by `node scripts/analyze_impact.mjs`. Do not edit by hand: it is overwritten.
Every word below, the interpretation at the bottom included, comes out of that program,
from the run files in `evidence/impact/runs` and from `evidence/impact/interpretation-v1.md`.
To check the committed file against the runs without writing anything, run the same
command with `--check` on the end.

**The participants were language models, not people.** This measures whether an agent
produces a first notice that is complete under this insurer's own rules, with and
without the page publishing those rules as typed tools. It measures nothing about time,
effort, satisfaction or real claims. The protocol is `evidence/impact/protocol-v1.md`, written before
any run it covers. What protocol v1 promised and its runs did not deliver is listed in
`evidence/impact/errata-v1.md`, which is worth reading before any number here.

**Three answers were already on the file before any run was scored.** The scorer builds
its draft from the demo fixture the page opens on, and that fixture arrives with
`incident_date`, `incident_type` and `driver` filled in. Every count below is what a
model produced combined with those three. It is not a count of claims an agent completed
on its own, and the section under the counts shows what is left when they are removed.

## The three answers already on the file, and the counts without them

`scoreRun` in `evidence/impact/scoring.mjs` starts every draft with
`createClaim(fixtures/demo-collision.json)`. That file is the demo the page opens on and it
carries `incident_date`, `incident_type` and `driver` already answered and badged `policy`.
None of the six briefs in `scenarios.json` states a date or says who was driving, so no run
in either arm could have produced `incident_date`, and every run in both arms is credited
with it anyway. The Policy complete column is a property of the model values plus those
three answers. Reading it as work the agent did would be wrong.

Sensitivity, from the same run files scored a second time with the fixture replaced by the
policy alone and nothing pre-filled:

- **published-rules**: 5 policy complete out of 18 with the three answers on file, and 0 out of the same 18 without them.
- **static-form**: 6 policy complete out of 18 with the three answers on file, and 0 out of the same 18 without them.

The requirement that closes on the seed is `date_of_loss` in the Northwind pack, which reads
`incident_date`. The published counts are not re-scored and not withdrawn. They are printed
next to the number that says what they rest on.

## What this says, including the part that does not flatter the page

This file is the one hand written part of `results.md`. The analyzer reads it and inlines it, so the
artifact reproduces byte for byte from the runs and this text together. Nothing here may state a
number the tables above do not already carry.

**The page did not beat a good static form on this measure.** Counting the three answers the demo
fixture already had on file, five of eighteen runs against the published rules came out policy
complete and six of eighteen against the static form did. Take those three answers away and both
arms are zero. The page's arm also left more open on average and produced two runs whose values
contradicted the scenario, against none in the control.

**The absolute counts are not a score for either arm.** No run in either arm produced an incident
date, because no brief contains one, and the date closes the requirement the pack calls
`date_of_loss`. So the honest reading of this study is the comparison between the two arms under
identical seeding, not the size of either number. The comparison still goes against the page.

**It is published because it was measured.** The protocol fixed the measure before the runs
happened, and a result that went the other way is the reason a preregistration is worth having. No
sentence in the README, the submission description or the video cites this as impact, and the honest
limit those files already carry, that nobody has run ClaimReady on a real intake, is unchanged.

**The likeliest reason, from the runs themselves.** The agent arm most often left `damage_zone`
empty, nine times out of eighteen, then `location` six times. The control was handed one form
listing every field at once and answered it in a single turn; the agent had to discover the same
fields through tools and stopped when it judged itself done. That is a finding about how an agent
works a tool surface, not about whether the surface is correct, and the first version of this
harness surfaced a real defect behind part of it: the tool surface never told an agent what a clock
position meant, while the page's own select had always said it. That is fixed, and it is a change
this study paid for.

**What this measure does not cover, and what a fair reading should not conclude.** Completeness of a
first notice is one thing a page can be judged on. It says nothing about the requirements that only
a policy knows, the tools that appear and vanish with the claim, the refusals, the pinning, or the
route each answer took, which are the things this entry is actually about and which a static form
cannot do at all. A better study would measure those. This one measured what it said it would, and
`evidence/impact/errata-v1.md` lists the places where it did not even do that.
